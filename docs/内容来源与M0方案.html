Content Sourcing & M0 Scope

内容不是找不到
是「讲解」必须自己写

法语例句、变位、母语音频、语法大纲——这些网上确实都有，而且有相当一部分是开放许可的。 但面向中文母语者的「讲解」几乎不存在可复用的开放语料。这份文档把可获取的部分、必须自写的部分、 以及 M0 到底做多少，一次说清楚。

00结论先行

三句话，决定后面所有事。

可以白拿的
70%

法语例句（Tatoeba，CC BY）、母语音频（FSI 公版 / Common Voice CC0 / Français interactif CC BY）、动词变位（verbecc）、语法大纲（Wikibooks CC BY-SA）。

必须自己写的
30%

中文讲解、中国人易错点、干扰项设计、题目与知识点的对应关系。这部分没有任何开放语料可以直接搬。

绝对不能碰的
0

Kwiziq / Lawless French 的课文与题库、TV5Monde、RFI、Duolingo、沪江/法语角等版权保留内容。

最关键的判断：你担心的「音频和讲解」其实是两类完全不同的东西。音频是工程问题——用本地 TTS 批量生成，2 秒一条，零版权风险，M0 阶段就能全量覆盖。讲解是写作问题——但它比想象中便宜：一个知识点只需要 120 字规则 + 2 组对比例句 + 1 条易错点，熟练后 8–10 分钟一个。

所以真正的成本不是「找内容」，而是「把法语素材对齐到知识点，并用中文重写一遍」。这条流水线我已经搭出可运行的骨架（见第五节与 tools/）。

另一个必须先纠正的预期：不存在「下载一个包就拥有 500 个知识点」的捷径。开放教材（如 Français interactif）是按课组织的，不是按「可独立测试的规则」组织的。从教材到知识点，中间必须做一次拆解——这正是 6.1 节说的 45–55 人日里最花时间的部分，也是产品差异化的来源。

02五层内容策略

一个知识点由五种材料组成，每种材料的获取方式完全不同。

层获取方式自动化程度说明
① 大纲人工整理 + LLM 辅助半自动从公开语法目录提取主题，按「可独立测试」拆成 320 条，再标级别与先修。事实性清单不受版权保护。
② 素材Tatoeba API 检索 + 人工挑选可脚本化按句型正则检索，过滤长度、语域、翻译质量。候选 20 条里挑 3 条，再改写。
③ 音频Piper 批量合成全自动输入 JSON，输出 tts/fr/{kp_id}/{n}.wav。一条约 0.5–2 秒。
④ 讲解模板 + LLM 起草 + 人工定稿半自动固定三槽位：一句话规则 / 2 组对比 / 1 条易错。LLM 只能起草，必须人工核对语法与中文表达。
⑤ 题目模板 + 人工设计干扰项手工干扰项必须来自真实错误（如 *est parti），不能随机替换。这是题目质量的分水岭。

为什么不用 LLM 直接生成全部内容？可以生成 80% 的初稿，但法语语法细节（性数配合、介词、语域）错误率不低，而语言学习产品对错误的容忍度是零——教错一次，用户会记很久。正确用法是：LLM 起草 + 规则校验（verbecc/拼写）+ 人工抽检 100% 的 primer 与 20% 的题目。

03重点来源实测

不是「听说有」，是「我调通了」。

① Tatoeba：例句 + 中文翻译，API 可直接用已验证

实测请求：检索包含 n'ai pas de 的法语例句，要求有中文翻译，返回 153 条；每条都带许可字段、翻译分组、音频列表。

GET https://tatoeba.org/en/api_v0/search
    ?from=fra&to=cmn&query=n%27ai%20pas%20de&sort=relevance

// 返回（节选）
{
  "text": "Je n'ai pas de livre.",
  "license": "CC BY 2.0 FR",
  "audios": [],
  "translations": [[{ "text": "我没有书。", "lang": "cmn" }]]
}

这解决了两件最难的事：地道的法语句子和现成的中文翻译。但有两个坑：

  • 音频许可不在 API 里。实测 audios[].license 返回 null，必须去贡献者主页逐条确认。所以不要用 Tatoeba 的音频，改用 TTS。
  • 翻译不一定贴题。「Bonjour」有「你好 / 下午好 / 早上好」三种译法，必须人工挑一个与例句语境匹配的。

② Français interactif：唯一「课程 + 音频 + 语法 + 练习」全齐的开放教材CC BY

COERLL 官方描述：13 章第一年法语课程，含 320+ 视频、词汇与语音音频、在线语法参考 + 自校正练习、音频对话、变位工具。许可为 CC BY（可改编、可商用、需署名）。

它的价值不在于「直接抄」，而在于三点：语法页的结构可以照着重写（规则 → 对比例句 → 练习），音频对话可以做听力题，章节顺序可以作为 A0–A1 的先修依据。

③ FSI：公版，但别指望它现代Public Domain

FSI 法语基础课程是 1960 年代为美国外交官开发的，PDF + 数十小时母语录音，美国政府作品，公版。优点是句型密度高、drill 设计严谨；缺点是语料老旧（telephone、cassette 之类的场景），且以英语为母语者设计。适合做听力素材库，不适合做产品的主例句。

④ 音频：Piper 是当前最稳的本地方案已验证声音清单

声音质量许可结论
fr_FR-siwis-mediummediumCC BY 4.0默认。单说话人、清晰、许可干净
fr_FR-mls-mediummediumCC BY 4.0125 个说话人，可做「换个人读」的听力变体
fr_FR-upmc-mediummediumCC BY-SA 4.0可用，但 ShareAlike 有解释成本，非首选
fr_FR-tom-mediummediumAGPLv3不用。传染性许可
fr_FR-gilles-lowlow—音质不足，不用

另：Kokoro-82M（Apache 2.0）含 fr-fr 声音，自然度更好，可作为 B 方案；Common Voice（CC0）适合做真实人声的听写素材。

⑤ 变位：verbecc 生成，不搬维基LGPL

verbecc 支持数千法语动词的完整变位（含复合时态、代词式动词、阴/阳性第三人称），并能用机器学习预测未登录词（约 99% 准确）。作为库调用即可，避免从 Wiktionnaire 批量搬表带来的 CC BY-SA 传染。

04版权边界

四档，越往下越危险。

档位含义典型来源与做法
A 自由使用公版或 CC0，无署名义务FSI、Gutenberg、LibriVox、Common Voice。可任意改写、商用。
B 署名可用CC BY，可改编商用，需在「关于」页署名Français interactif、Tatoeba 文本、Piper siwis/mls 声音。产品里放一个「内容来源」页，列出来源、作者、许可链接。
C 只查证不搬运CC BY-SA / LGPL，直接改编会触发同许可Wikibooks、Wiktionnaire、Lexique。用来核对规则与变位，不整段复制。verbecc 作为库调用。
D 不可用版权保留，任何形式的复制/翻译/洗稿都侵权Kwiziq、Lawless French、TV5Monde、RFI、Duolingo、沪江、法语角。只能人工阅读后用自己的话重写，且不能照搬例句结构。

三个容易踩的坑：

① 「换几个词」不算原创。把 Kwiziq 的例句改两个词，仍然可能构成演绎侵权。

② CC BY-SA 会传染。如果把 Wikibooks 的段落改写进你的讲解，那段讲解可能需要以 CC BY-SA 发布。规避方式：只提取「讲什么」，不提取「怎么讲」。

③ Tatoeba 音频许可不明。API 不返回许可，逐条确认成本极高。统一用 TTS，既干净又一致。

05内容管线

七步，从「一个语法主题」到「可入库的知识点」。

管线已经落到仓库里：

content/
├─ sources.json          # 来源注册表：URL / 许可 / 用途 / 署名文本
├─ schema/kp.schema.json # 知识点 JSON Schema
└─ kp/*.json             # 每个知识点一个文件
tools/
├─ fetch_tatoeba.py      # 按句型检索候选例句（含中文翻译）
├─ tts_piper.py          # 批量合成例句音频
└─ validate_content.py   # schema + 引用完整性校验

实测：一条命令拿到候选例句

$ python tools/fetch_tatoeba.py --query "n'ai pas de" --limit 8

  1. Je n'ai pas de livre.                      我没有书。            [audio: no]
  2. Je n'ai pas de temps.                      我没有时间。          [audio: no]
  3. Il n'y a pas de problème.                  没问题。              [audio: no]
  ...
  # 输出 content/candidates/negation_ne_pas.json，含 id / 许可 / 翻译 / 音频标记

这个脚本只做「候选收集」，不做自动入库——因为例句是否贴题、翻译是否自然，必须人看。工具的价值是把 30 分钟的手工搜索压到 30 秒。

06单点生产 SOP

一个知识点从空白到可上线，标准工时 25–35 分钟。

步动作工时产出 / 标准
1写 ID、级别、标题、先修2 minfr.a1.negation.ne_pas；先修至少 1 条
2写 primer 三槽位8 min规则 ≤ 60 字；对比 2 组；易错 1 条（必须是中国人会犯的）
3检索并挑选例句5 min2–4 条，长度 4–12 词，语域为日常
4写 8 道题12 min2 单选 + 4 填空 + 1 改错 + 1 翻译；每题有解析
5合成音频1 min每条例句 1 个 wav，命名 {kp_id}-ex{n}.wav
6校验2 minschema 通过；变位正确；答案唯一（或有 accept 列表）
7抽检3 min换一个人（或隔天自己）盲做 3 题，能全对才算过

按 30 分钟 / 点计算：20 点 ≈ 10 小时（约 1.5 个工作日）；320 点 ≈ 160 小时（约 20 个工作日）——比 6.1 节估计的 45–55 人日更低，因为例句和音频被工具省掉了。这是本次调研带来的最大成本修正。

成本重估：原方案按「全手工写例句 + 录/找音频」估 45–55 人日；引入 Tatoeba + Piper 后，例句与音频几乎零成本，320 个知识点的内容成本降到约 20–25 人日。M0 的 20 个点可以在 1.5 天内完成。

07M0 范围

5 天，只证明一件事：机制跑得通，内容造得出。

M0 的成功标准不是「好看」，而是：拿 20 个真实知识点，走完一次完整的「学 → 测 → 评分 → 重排」，并且分数曲线符合直觉。

模块做不做（留给 M1+）
内容 20 个知识点（A0 8 / A1 7 / A2L 5），每点 1 段 primer + 8 题 + 2–4 条例句 + 音频，共 160 题 不追 320 点；不做 B1 以上；不做阅读理解
数据 JSON Schema、SQLite 建表、seed 导入、全量导出 不做增量同步、不做多用户
引擎 BKT 更新、展示分（含负分与收缩）、FSRS 调度、10 题组卷（配额 + 打分 + 约束）、预学习状态机 不做 Elo 题目校准；不做级别分稀释的可视化
界面 3 页：Dashboard（静态）、Kwiz Runner（作答 + 即时反馈）、结果页（逐题对照） 不做 Brainmap、分级测试、Notebook、成就、通知、Tauri 打包
工具 Tatoeba 抓取、Piper 合成、内容校验三个脚本 不做后台管理界面

08风险与决策

开工前需要你拍板的三件事。

风险等级对策
Tatoeba 例句质量参差中只取「有中文翻译 + 长度 4–12 词 + 无脏话标签」的句子，再人工改写；不追求数量。
TTS 发音不准（联诵、省音）中Piper 对短句表现好；对含联诵的句子人工试听，必要时换 Kokoro 或改写句子。
LLM 起草的讲解有语法错误高讲解必须人工定稿；用 verbecc + 拼写检查做机器校验；建立「已审」标记，未审不得入库。
CC BY-SA 传染中Wikibooks/Wiktionnaire 只查证不搬运；所有入库内容在 sources.json 记录来源与许可。
20 个点撑不起「像 Kwiziq」的感觉中M0 只验证机制，不验证内容丰富度；Brainmap 留到 M2，避免用 20 个点画出稀疏地图。

决策点选项我的建议
M0 内容量20 点 / 10 点20 点。10 点不够覆盖 4 个功能块的组卷约束，会测不出问题。
音频方案Piper / Kokoro / 真人录音Piper siwis。先跑通，M2 再评估是否换 Kokoro 提升自然度。
是否引入 LLM 起草全人工 / LLM 起草 + 人工定稿LLM 起草 + 人工定稿。但讲解必须 100% 人工过一遍，不能省。
